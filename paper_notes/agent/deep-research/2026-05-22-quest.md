## 1. 一句话总结

Quest 的核心思想是：**用统一的 Rubric Tree 表示不同类型 DeepResearch 任务的评价标准，并基于真实网页自动合成 objective 与 open-ended 两类训练任务；再结合结构化上下文管理、Mid-Training、SFT 和 GRPO RL，训练出覆盖事实检索、引用 grounding、报告综合三类能力的开源 DeepResearch Agent。**

更短地说：

```text
Quest = fully synthetic rubric-tree tasks + context condenser + MT + SFT + GRPO RL
```

论文最重要的观点：

```text
DeepResearch Agent 不应该只训练“找一个隐藏事实答案”，
还要训练“按多维标准完成可引用、可验证、可综合的研究任务”。
```

## 2. 论文定位

### 2.1 Quest 想解决什么问题

现有 DeepResearch Agent 有两类问题：

1. **闭源系统强但不可复现**：OpenAI Deep Research、Gemini Deep Research、Claude Research 等效果强，但训练 recipe、数据、模型不公开；
2. **开源系统能力覆盖不均衡**：一些开源 DeepResearch Agent 只擅长事实检索，一些擅长长报告，一些擅长引用 grounding，但很少同时覆盖三类能力。

Quest 把 DeepResearch Agent 的核心能力拆成三类：

| 能力 | 含义 | 代表任务 |
|---|---|---|
| Fact Seeking | 在网页中通过多跳搜索找到精确信息 | BrowseComp、HLE、GAIA |
| Citation Grounding | 回答必须由可靠 URL 支撑，引用可验证 | Mind2Web 2 |
| Report Synthesis | 综合多源信息形成结构化长报告 | DeepResearch Bench、LiveResearchBench |

Quest 的目标是训练一个 general-purpose deep research agent，而不是只优化某一种 benchmark。

### 2.2 和前面几篇论文的关系

| 论文 | 主要贡献 | Quest 的关系 |
|---|---|---|
| Tongyi DeepResearch | MT/SFT/RL 全流程，环境交互 | Quest 也采用 MT -> SFT -> RL，但更强调开源可复现和 rubric-tree 合成 |
| REDSearcher | 可控复杂任务合成，模拟环境 | Quest 同样关注合成任务，但用 rubric tree 统一 objective/open-ended 评价 |
| S1-DeepResearch | 图驱动任务与多维轨迹验证 | Quest 的 rubric tree 也是一种结构化任务/评价表示 |
| MiroThinker | Interactive Scaling 和 Agentic RL | Quest 使用工具调用、长程轨迹、GRPO 和缓存基础设施 |
| RubricEM | Rubric 作为 RL 共享接口 | Quest 的 rubric tree 主要用于数据合成和 reward，而 RubricEM 更强调阶段化 credit |

Quest 和 RubricEM 都强调 rubric，但侧重点不同：

| 论文 | Rubric 的主要作用 |
|---|---|
| Quest | 统一生成任务、评价任务、构造 reward |
| RubricEM | 指导 Agent 执行、stagewise judge、credit assignment、reflection memory |

## 3. 核心贡献

论文列出的贡献可以总结为五点。

### 3.1 发布 Quest 模型族

Quest 是一组 open models，规模从 2B 到 35B。

论文重点报告：

- Quest-2B-SFT；
- Quest-4B-SFT；
- Quest-9B-SFT；
- Quest-30B；
- Quest-35B。

核心模型 Quest-35B 基于 Qwen3.5-35B-A3B 训练。

### 3.2 提出 Quest-8K 合成数据集

Quest 使用约 8K 个合成任务进行 SFT 和 RL。

这些任务不是简单问答，而是每个任务包含：

```text
complex query + query-specific rubric tree + evaluation protocol
```

这让任务既能生成，也能自动评价。

### 3.3 用 Rubric Tree 统一不同任务类型

Rubric Tree 是一棵树：

- root：整体分数；
- internal nodes：高层评价维度；
- leaf nodes：可直接验证的原子标准；
- score：从叶子向上聚合。

它可以表示：

- 唯一答案任务；
- 多答案任务；
- 多约束 objective 任务；
- open-ended 报告任务；
- citation grounding 任务。

### 3.4 提出结构化 Context Management

Quest 不直接保留全部历史，也不简单 discard-all，而是用 Context Condenser 把长程工具交互压缩成 `Context State`。

Context State 分三类信息：

| Bucket | 含义 | Agent 如何使用 |
|---|---|---|
| Trusted | 已被来源验证的事实 | 可直接用于回答 |
| Untrusted | 被其他来源反驳或不可靠的 claim | 降低优先级，避免复用 |
| Uncertain | 尚未确认、需要后续验证的 claim | 指导下一步搜索或访问 URL |

这相当于给 Agent 维护一个结构化认识状态。

### 3.5 提出完整训练 recipe

Quest 的训练流程：

```text
Mid-Training -> Supervised Fine-Tuning -> Reinforcement Learning
```

每个阶段职责：

| 阶段 | 作用 |
|---|---|
| MT | 训练模型理解长上下文、网页噪声和 Context State |
| SFT | 模仿高质量工具调用轨迹 |
| RL | 用 rubric-tree reward 和 fact-checking reward 优化策略 |

## 4. 为什么只做单答案合成不够

很多 DeepResearch 数据合成方法会生成类似问题：

```text
找到满足若干条件的某个实体。
```

这类任务适合 BrowseComp：答案是一个隐藏实体，reward 可以 exact match。

但它有两个局限。

### 4.1 泛化范围窄

单答案任务主要训练：

- 搜索；
- 多跳定位；
- 最终短答案。

但真实 DeepResearch 常需要：

- 多源信息聚合；
- 多视角比较；
- 风险和限制分析；
- 结构化报告；
- 引用支撑；
- 解释和建议。

### 4.2 Reward 太粗

单答案任务通常只有：

```text
正确 = 1
错误 = 0
```

但长研究报告的质量是多维的：

- 覆盖是否完整；
- 证据是否可靠；
- 引用是否正确；
- 推理是否有洞察；
- 结构是否清晰；
- 是否符合指令；
- 是否有错误或幻觉。

因此 Quest 用 Rubric Tree 提供 fine-grained reward。

## 5. Rubric Tree 详解

### 5.1 Rubric Tree 的基本结构

Rubric Tree 是层级化评价树。

```text
Root: Overall Score
  -> Criterion A
      -> Leaf A1
      -> Leaf A2
  -> Criterion B
      -> Leaf B1
      -> Leaf B2
```

每个叶子节点是一个可直接判断的原子标准。

例如 objective 任务：

```text
问题：识别 2024 年美国两个造成死亡的李斯特菌疫情，并判断哪个更致命。

Root
  -> Outbreak 1
      -> 来源是 Boar's Head deli meats
      -> 死亡人数为 10
  -> Outbreak 2
      -> 来源是 Rizo-López queso fresco / cotija
      -> 死亡人数为 2
  -> Comparison
      -> 判断 Boar's Head 更致命
      -> 用 10 vs 2 死亡人数作为证据
```

Open-ended 任务示例：

```text
问题：评估 Apple 进入折叠屏手机市场。

Root
  -> Comprehensiveness
      -> 对比 Samsung Z Fold
      -> 对比 Huawei Mate X
      -> 覆盖铰链/屏幕供应链
  -> Insight
      -> 分析采用障碍
      -> 讨论后发策略
  -> Instruction Following
      -> 覆盖定价策略
      -> 覆盖技术比较
  -> Readability
      -> 层次清晰
      -> 少用术语
```

### 5.2 Rubric Tree 的优势

| 问题 | Rubric Tree 如何解决 |
|---|---|
| 单答案过窄 | 可表示多答案、多约束、长报告 |
| reward 太粗 | 叶子节点提供部分得分 |
| open-ended 难评估 | 用共享维度 + 任务特定子标准 |
| 自动合成难控 | 树结构可过滤、可验证、可执行 |
| RL 信号稀疏 | root partial score 可作为细粒度 reward |

### 5.3 Critical 和 Non-critical 节点

Quest 的 objective rubric tree 中，节点分为：

| 节点类型 | 含义 | 评分影响 |
|---|---|---|
| Critical | 必须满足的关键条件 | 失败会导致父节点失败 |
| Non-critical | 可部分给分的条件 | 失败不一定让父节点全失败 |

例子：

- 如果任务要求“必须提供官方来源 URL”，这个节点可能是 critical；
- 如果任务要求列出 4 个可选酒店，每个酒店节点可以是 non-critical，从而允许部分正确。

### 5.4 Sequential 和 Parallel 聚合

中间节点可以是：

| 聚合方式 | 含义 | 示例 |
|---|---|---|
| Sequential | 子节点有逻辑顺序，前一步失败会影响后续 | 先找到论文，再找该论文最后作者信息 |
| Parallel | 子节点独立评价 | 同时提供作者、年份、出版社 |

这非常重要，因为很多复杂任务不是简单平均。

例如：

```text
如果第一步找错实体，后面对该实体的属性查询即使格式正确，也不应得到完整分数。
```

### 5.5 Leaf node 原子性

Quest 要求叶子节点：

- 只表示一个明确标准；
- 可以 true/false 判断；
- 不混合无关条件；
- 能追溯到问题或提取的 constraints；
- 不引入额外要求。

坏例子：

```text
“答案要准确、完整、有洞察。”
```

好例子：

```text
“答案必须给出该公司 2024 年官方披露的年度收入，并引用来源 URL。”
```

### 5.6 防止 hard-coded answer

论文非常强调：rubric tree 不能把“需要被发现的答案”硬编码进去。

不允许：

```text
如果问题要求模型找出满足条件的 ETF，rubric 不能写“必须是 Franklin Templeton XRP ETF”。
```

应该写成：

```text
答案选择的 ETF 必须满足题目中的资产类别、费用、上市地、发行方等约束。
```

原因：如果 rubric 中写死答案，任务就退化成答案泄漏，不再考察真实检索和推理。

### 5.7 复杂度控制

Objective task 的 rubric tree 使用 Breadth × Depth 组合控制复杂度。

Breadth：

| Level | 节点宽度 |
|---|---|
| B1 Narrow | 每层 1-3 个节点 |
| B2 Moderate | 每层 4-11 个节点 |
| B3 Broad | 每层 12 个以上节点 |

Depth：

| Level | 树深度 |
|---|---|
| D1 Shallow | 2 层 |
| D2 Standard | 3-4 层 |
| D3 Deep | 5-6 层 |

组合成 C1-C9：

| Class | Breadth | Depth | 含义 |
|---|---|---|---|
| C1 | 1-3 | 2 | 简单直接任务 |
| C2 | 1-3 | 3-4 | 单方向中等深度 |
| C3 | 1-3 | 5-6 | 窄但深的专业探索 |
| C4 | 4-11 | 2 | 多属性但浅 |
| C5 | 4-11 | 3-4 | 最常见、较平衡 |
| C6 | 4-11 | 5-6 | 多角色、多约束、深推理 |
| C7 | >=12 | 2 | 高维但浅 |
| C8 | >=12 | 3-4 | 宽并行、标准深度 |
| C9 | >=12 | 5-6 | 最高复杂度 |

这和 REDSearcher 的“图复杂度 + 证据分散度”有相似思想。

## 6. 数据合成流程

Quest 的数据合成目标：

```text
自动生成复杂 query、rubric tree 和可执行 evaluation protocol。
```

论文使用的主要合成模型 `G_syn` 默认是 Claude Sonnet 4.5。

### 6.1 Objective Tasks 合成流程

Objective task 是有相对客观验证标准的任务。

流程：

```text
1. 从 Google Trends 抽取 trending keywords
2. G_syn 根据关键词自主搜索网页
3. 收集相关网页证据
4. 从证据中抽取 verifiable constraints
5. 组织成 rubric tree
6. 对 rubric tree 做 iterative refinement
7. 用 Claude Sonnet 4.5 做 tree verification
8. 失败任务丢弃
9. 将 rubric tree 转成自然语言问题
10. 用 GPT-5 生成 Python evaluation script
11. 删除脚本错误样本
12. 得到 objective training tasks
```

每个 objective 样本包含：

```json
{
  "query": "自然语言任务",
  "rubric_tree": "层级评价树",
  "evaluation_protocol": "Python script",
  "solution": "证据支撑的参考解"
}
```

### 6.2 Objective Task 的关键约束

合成 prompt 要求：

- 任务必须现实、有实际需求；
- 必须需要长程搜索，不是几步就能完成；
- 问题必须清晰、客观、无歧义；
- 不允许视频理解；
- 不允许非英文网站；
- 不允许外部专用工具；
- 不允许快速变化答案；
- 不允许无界 top-k / cheapest / list all；
- verification 尽量能分解成单页验证；
- visit URL 必须来自 search results，不能猜 URL。

这些规则非常工程化，目的都是减少合成数据中的幻觉、不可验证和不可执行任务。

### 6.3 Open-ended Tasks 合成流程

Open-ended task 是需要长报告综合的任务。

流程：

```text
1. 从 trending keywords 开始
2. G_syn 自主搜索和访问网页
3. 提出一个开放式研究问题
4. 生成 grounded Markdown solution
5. 构造 open-ended rubric tree
6. 生成 reference report
7. 对候选 report 和 reference report 做 pairwise scoring
```

Open-ended task 的 root 下固定四个共享维度：

| 维度 | 含义 |
|---|---|
| Instruction Following | 是否按用户要求覆盖指定内容 |
| Comprehensiveness | 覆盖是否完整，信息是否充分 |
| Readability | 结构、清晰度、语言可读性 |
| Insight | 是否有分析深度、因果解释、决策价值 |

每个维度下面的子节点是任务特定的。

例如“Apple 折叠屏手机”任务中：

- Comprehensiveness 下有市场基线、竞品对比、定价、供应链等；
- Insight 下有采用障碍、后发策略、场景分析、竞争反应等；
- Instruction Following 下检查是否覆盖题目要求的 4 个方面；
- Readability 下检查结构、术语、图表、数字解释等。

### 6.4 Open-ended 权重生成

Open-ended rubric tree 中每个节点有权重。

论文做法：

```text
用 G_syn 生成权重三次，然后取平均。
```

原因：

- 单次权重生成可能随机；
- 多次平均提高稳定性；
- 不同任务的四大维度权重应不同。

例如：

- 投资指南更重视 comprehensiveness 和 instruction following；
- 市场战略分析更重视 insight。

### 6.5 Open-ended 评价协议

Open-ended task 的 evaluation protocol 包含三部分：

```text
reference report + rubric-based judge + pairwise normalization
```

给定候选报告 `r_cand` 和参考报告 `r_ref`：

1. Judge 同时看到 candidate 和 reference；
2. 对每个 rubric node 分别给 candidate 和 reference 打 0-10 分；
3. 聚合得到 `J(r_cand)` 和 `J(r_ref)`，范围 [0,1]；
4. 最终分数：

```text
Score = J(r_cand) / (J(r_cand) + J(r_ref))
```

解释：

- Score > 0.5：candidate 超过 reference；
- Score = 0.5：candidate 和 reference 接近；
- Score < 0.5：candidate 不如 reference。

这个设计是为了解决 pointwise judge 高分膨胀的问题。

## 7. 数据过滤与质量检查

### 7.1 任务过滤数量

论文报告的过滤过程：

| 类型 | 阶段 | 保留数量 |
|---|---|---:|
| Objective | 初始生成 | 17,000 |
| Objective | rubric refinement 后 | 8,737 |
| Objective | rubric tree verification 后 | 6,230 |
| Objective | 删除 Python script 错误后 | 5,934 |
| Open-ended | 初始生成 | 3,000 |
| Open-ended | 删除 invalid format 后 | 2,856 |
| Open-ended | 删除 unqualified tasks 后 | 2,498 |
| Open-ended | 删除低 reference report score 后 | 2,227 |

可以看到 retention rate 并不高。论文主动采用严格过滤。

### 7.2 Python evaluation script 人工检查

Objective task 的 evaluation script 由 GPT-5 生成。

论文抽样 50 个脚本，由 4 名 CS 研究生人工检查。

发现：

- 2 个有不可执行问题；
- 6 个有 rubric 相关错误。

常见错误：

1. 引入原任务没有要求的冗余 rubric 节点；
2. 只检查最终答案字面内容，而不是严格验证真实性；
3. 当答案没有 cited URLs 时，没有明确判负。

论文结论是：虽然不完美，但大多数脚本可以支持大规模自动评价。

### 7.3 这个质量检查的意义

Quest 的“完全合成”不是一次生成就相信，而是：

```text
生成 -> refinement -> verification -> 脚本执行检查 -> 人工抽检
```

这对任何合成数据项目都非常重要。

## 8. Context Management 详解

### 8.1 为什么需要 Context Condenser

DeepResearch Agent 会不断产生：

- 搜索 query；
- 搜索结果；
- visit 的网页内容；
- 中间 reasoning；
- 代码执行结果；
- 已经访问过的来源；
- 已确认和未确认的事实。

如果全部放进上下文：

- 上下文很快爆掉；
- 噪声变多；
- 模型注意力分散；
- 旧事实被遗忘；
- 重复搜索增加成本。

已有做法：

| 方法 | 问题 |
|---|---|
| Discard-all | 清空历史，Agent 会重复找已验证事实 |
| Keep-last-N | 只保留最近内容，可能丢掉早期关键证据 |
| 长上下文全塞 | 成本高，噪声大，训练困难 |

Quest 采用结构化压缩。

### 8.2 Context State 三个 bucket

Context State 是一个 JSON 对象。

核心字段：

```json
{
  "search_queries": [],
  "visited_sources": [],
  "information_state": {
    "trusted": [],
    "untrusted": [],
    "uncertain": []
  }
}
```

#### Trusted

保存已验证事实。

要求：

- 有 source URL；
- 从 visit 工具结果中直接支持；
- 具体、可用于最终回答；
- 不需要重复检索。

#### Untrusted

保存被反驳或不可靠的 claim。

要求：

- 说明为什么不可信；
- 指出矛盾来源；
- 防止模型后续误用。

#### Uncertain

保存未确认但可能有用的 claim。

要求：

- 说明缺什么；
- 给出具体 next action；
- 例如 visit 某 URL 或 search 某 query。

### 8.3 触发机制

当 context usage 超过阈值时：

```text
raw history -> Context Condenser -> updated Context State -> fresh context window
```

论文中的阈值：

```text
context threshold = 16K tokens
```

Context Condenser 使用 GPT-5-mini。

### 8.4 Context State 的作用

对后续 Agent：

| 信息状态 | 使用方式 |
|---|---|
| Trusted | 直接引用，不重复查 |
| Untrusted | 降低优先级，避免误用 |
| Uncertain | 指导下一步 search/visit |
| Search queries | 避免重复搜索 |
| Visited sources | 避免重复访问 URL |

这让 Agent 拥有一种“认识论状态”：

```text
我知道什么，我怀疑什么，我还需要查什么。
```

### 8.5 为什么它适合训练

论文强调：discard-all 和 keep-last-N 也许在短 benchmark 推理时还能用，但作为训练范式不可靠。

原因：

```text
训练样本中的 supervision 需要完整、连贯、跨长程轨迹一致。
如果压缩策略随机丢掉关键事实，模型会学到不稳定行为。
```

Context Condenser 使长轨迹可以拆成 session-level 训练，同时保持知识状态连贯。

## 10. Trajectory Collection 详解

### 10.1 Teacher 轨迹生成

SFT 需要完整 Agent trajectory。

论文使用：

```text
G_traj = Tongyi DeepResearch
```

对 open-ended task：

```text
使用 GPT-5.2 polish final report
```

每个 query：

1. Teacher 调用工具解决任务；
2. 用该任务的 evaluation protocol 打分；
3. 分数超过阈值则保留；
4. Objective 任务若失败，则做 reflection-based retry。

### 10.2 保留阈值

| 任务类型 | 阈值 ε |
|---|---:|
| Objective | 1.0 |
| Open-ended | 0.475 |

解释：

- Objective 任务要求完全正确；
- Open-ended 任务允许低于 reference report 但接近可用，因为 open-ended judge 分数本身有噪声。

### 10.3 Reflection-based retry

对于 objective task，若初始 teacher trajectory 未达标：

```text
将 evaluation protocol 给出的细粒度错误结果注入 prompt
让 teacher 重新尝试
如果 retry 后达标则保留
```

论文设置：

- 每个任务初始 rollout 5 次；
- 失败轨迹额外 retry 3 次；
- 最大工具调用 100 turns；
- context threshold 16K。

### 10.4 Inline Citation Format

Quest 标准化最终回答的引用格式。

做法：

```text
用 GPT-5-mini 回看 reasoning trace 和 Context State，
为最终回答中的事实 claim 插入对应 URL citation。
```

意义：

- 提高报告可验证性；
- 统一 SFT 输出风格；
- 为 RL 阶段 fact-checking reward 做准备。

## 11. Mid-Training 详解

### 11.1 MT 的作用

Quest 的 MT 不是传统领域继续预训练，而是 agentic mid-training。

目标是让 base model 提前学会：

- 处理长上下文；
- 从网页噪声中抽取目标信息；
- 生成 Context State；
- 理解 trusted/untrusted/uncertain；
- 适应后续长程工具交互。

### 11.2 Task 1：Context Summarization

输入：

```text
长历史上下文，包括搜索、访问、推理、旧 Context State
```

输出：

```text
新的 Context State JSON
```

模型要学会：

- 合并 prev_state；
- 去重 search queries；
- 去重 visited sources；
- 将 claim 放入 trusted/untrusted/uncertain；
- 对 uncertain 给出下一步具体行动；
- 不丢失关键已验证事实。

### 11.3 Task 2：Relevant Information Extraction

输入：

```text
raw HTML page + extraction goal
```

输出：

```text
和 goal 相关的信息摘要
```

模型要学会过滤：

- 导航栏；
- 广告；
- 页脚；
- 无关正文；
- 噪声内容。

这对真实 web research 很关键，因为网页不是干净文档。

### 11.4 MT 超参

|---|---|
| 优化方式 | Full-parameter |
| Precision | BF16 |
| LR | 3e-6 |
| Scheduler | Constant |
| Max context length | 24,576 |
| Per-device batch size | 2 |
| Gradient accumulation | 8 |
| Epoch | 1 |
| GPU | 32 × H100 |
| 时间 | 约 5 天 |

## 12. SFT 详解

### 12.1 Session-level training

Quest 不把完整 trajectory 当作一个超长训练样本，而是按 context condensation event 切成多个 session。

定义：

```text
一个 session = 两次 context condensation 之间的连续交互片段。
```

具体：

```text
从上一次 condensation 后的新工作上下文开始，
一直到下一次 condensation 前结束。
```

### 12.2 为什么不用 trajectory-level training

完整 trajectory 可能超过 200K tokens。

如果整条放入 GPU：

- 显存不可承受；
- batch size 太小；
- 训练效率低；
- 上下文长度受限。

Session-level training 优点：

1. 降低峰值显存；
2. 与真实 inference 的 working context 一致；
3. 配合 Context State 保持长程信息；
4. 允许训练超过原生上下文窗口的长任务；
5. 论文称可用 16 H100 训练超过 200K token 的轨迹。

### 12.3 SFT 目标

标准 next-token prediction。

但训练样本中包括：

- 工具调用；
- 工具返回后的状态更新；
- Context State 使用；
- 最终带引用报告；
- 长程研究过程。

### 12.4 SFT 超参

| 项目 | 值 |
|---|---|
| 优化方式 | Full-parameter |
| Precision | BF16 |
| LR | 3e-6 |
| Scheduler | Constant |
| Max sequence length | 32,768 |
| Per-device batch size | 1 |
| Gradient accumulation | 8 |
| Epoch | 3 |
| GPU | 32 × H100 |
| 时间 | 约 1 天 |

## 13. RL 详解

### 13.1 RL 算法

Quest 使用 GRPO-style outcome-based reinforcement tuning。

它没有像 RubricEM 那样做 stagewise reward，而是对整条 rollout 计算 scalar reward，再给该 rollout 的所有 session 相同 advantage。

### 13.2 Rubric-tree reward

对于 objective task：

```text
s_rubric = evaluation protocol 输出的 rubric tree score
```

对于 open-ended task：

先得到 pairwise raw score，再离散化：

| Pairwise score | s_rubric |
|---|---:|
| > 0.5 | 1.0 |
| [0.475, 0.5) | 0.75 |
| [0.45, 0.475) | 0.5 |
| [0.425, 0.45) | 0.25 |
| < 0.425 | 0 |

为什么离散化：

- 保留相对排序；
- 增强 reward 可分离性；
- 减少微小 judge 波动影响。

### 13.3 Fact-checking reward

Quest 额外加入 citation grounding reward。

流程：

```text
1. 从答案中抽取 cited fact-URL pairs
2. 去重
3. 重新获取被引用网页
4. 用 GPT-5-mini 判断每个 citation：supported / unsupported / unknown
5. 只在 supported 和 unsupported 中计算支持比例
```

公式：

```text
s_fact = supported citations / determinate citations
```

### 13.4 Final reward

最终 reward：

```text
R = 0.75 * s_rubric + 0.25 * min(s_fact, s_rubric)
```

这个公式很巧妙。

为什么用 `min(s_fact, s_rubric)`：

```text
如果答案内容很差，即使引用都支持，也不能靠 citation reward 拉高分。
```

例如：

| s_rubric | s_fact | min | R |
|---:|---:|---:|---:|
| 1.0 | 1.0 | 1.0 | 1.0 |
| 0.8 | 1.0 | 0.8 | 0.8 |
| 0.2 | 1.0 | 0.2 | 0.2 |
| 0.8 | 0.2 | 0.2 | 0.65 |

这防止模型学会“引用看起来很漂亮但没完成任务”。

### 13.5 Advantage 传播

对同一个 prompt 采样一组 rollouts。

每条 rollout 得到 scalar reward `R_i`。

组内标准化：

```text
A_i = (R_i - μ_g) / (σ_g + ε)
```

如果一个 rollout 被切成多个 session：

```text
同一 rollout 的所有 session 共享同一个 advantage。
```

论文还强调 normalization 时按 unique rollout 去重，避免一个长 rollout 因为 session 多而在统计上占更大权重。

### 13.6 RL 超参

| 项目 | 值 |
|---|---|
| 框架 | VERL fully asynchronous pipeline |
| 算法 | GRPO |
| Actor LR | 1e-6 |
| Responses per prompt | 8 |
| Global batch size | 64 |
| PPO mini-batch size | 16 |
| PPO mini-batches | 4 |
| Max prompt length | 24,000 |
| Max response length | 12,288 |
| Max single-turn response | 10,240 |
| Temperature | 1.0 |
| Max tool-call turns | 100 |
| Context threshold | 16K |
| Trainer GPUs | 16 × H100 |
| Rollout GPUs | 16 × H100 |
| Total GPUs | 32 × H100 |
| RL steps | 80 async training steps = 320 mini-batch optimization steps |
| KL penalty | 论文称优化标准 GRPO objective，排除 KL penalty |

## 14. 工具与基础设施

### 14.1 工具集

Quest 使用四类工具：

| 工具 | 作用 |
|---|---|
| Google Search | 检索相关网页结果 |
| Visit | 读取网页并按 goal 摘要 HTML 内容 |
| Python Interpreter | 执行计算 |
| Google Scholar | 检索学术论文 |

Visit 工具的 summary model 使用 GPT-5-mini。

### 14.2 为什么需要缓存

训练 DeepResearch Agent 时，以下阶段都会大量调用外部环境：

- 数据合成；
- SFT trajectory collection；
- RL rollout；
- 评价；
- fact-checking。

如果每次都访问 live API：

- 成本极高；
- 速度很慢；
- 结果不稳定；
- 难复现。

### 14.3 Search 和 Scholar cache

检索缓存策略：

```text
新 query -> exact-match cache lookup
         -> 如果命中，直接返回
         -> 如果未命中，FAISS semantic similarity lookup
         -> 如果相似度高，返回相似 query 的结果
         -> 如果仍未命中，调用 live API
         -> 写回 cache
```

Live API：Serper。

这个设计同时利用：

- 精确缓存；
- 语义近似缓存；
- live fallback。

### 14.4 Visit cache

Visit 缓存更简单：

```text
URL exact match -> hit 返回缓存页面
               -> miss 调用 live page API
               -> 写回 cache
```

Live API：Jina。

### 14.5 Fully asynchronous RL infrastructure

Quest 基于 VERL 异步训练，进一步把 evaluation 也异步化。

问题：rubric-tree evaluation 很慢。

论文报告：

```text
平均 evaluation 约 4 分钟，长尾可达 30 分钟。
```

同步训练会被慢 evaluator 卡住。

Quest 做法：

```text
rollout 一生成 -> 立即发给 evaluation Ray actors
trainer 不等整个 batch 全部评分完
shared queue 中累积足够 scored samples 后就异步更新
慢样本自然进入后续 batch
```

此外：

- evaluator timeout control；
- interruption-aware reward handling；
- 参数同步时可以恢复或重发 in-flight evaluations。

### 14.6 Fallback model

论文为了稳定 RL，给一些组件设置 fallback model。

例如：

| 用途 | 默认模型 | Fallback |
|---|---|---|
| RL Judge | Qwen3-4B | DeepSeek V3.2 |
| Visit Summary | GPT-5-mini | DeepSeek V3.2 |
| Context Condenser | GPT-5-mini | DeepSeek V3.2 |
| Fact-checking | GPT-5-mini | DeepSeek V3.2 |

fallback 触发率约 3%，但论文认为没有 fallback 会导致 RL 训练不稳定。

## 19. 失败尝试

Quest 很有价值的一点是专门报告了 unsuccessful attempts。

### 19.1 Search Result Prediction in Mid-training

尝试：

```text
让模型预测/生成搜索结果摘要，作为 mid-training 任务。
```

结果：

- 单独使用时对搜索重任务有帮助；
- 加入当前 MT 混合任务后整体性能下降。

可能原因：

```text
Search result prediction 和 Context Summarization 功能重叠，产生冲突学习信号。
```

启发：

```text
Mid-training 任务不是越多越好，目标重叠可能互相干扰。
```

### 19.2 Rubric-Based Error Identification in Mid-training

尝试：

```text
给模型一个答案和 rubric tree，让模型预测答案可能有哪些问题。
```

结果：

```text
只有边际提升。
```

可能原因：

- MT 阶段没有外部证据；
- 模型只能发现表面错误；
- 真正复杂事实错误依赖证据验证。

启发：

```text
错误识别必须接入证据环境，否则只是训练模型说空泛批评。
```

### 19.3 DPO for Report Comparison

尝试：

```text
用 rubric-tree score 构造 report preference pairs，训练 DPO。
```

结果：

```text
没有提升，训练不稳定，容易过拟合。
```

可能原因：

- 长报告差异维度多；
- rubric score 小差异不一定对应真实偏好差异；
- pairwise preference 构造成本高且噪声大；
- DPO 对长报告复杂偏好可能不够稳。

启发：

```text
不要假设 DPO 一定适合长报告；
对业务预测 Agent，也要谨慎构造偏好对，避免微弱分差 pair。
```

### 19.4 Open-ended Evaluation 的失败设计

#### Pointwise scoring 失败

做法：每个 rubric criterion 打 0 / 0.5 / 1。

问题：

```text
约 50% 样本接近满分，score inflation 严重，无法区分好坏。
```

原因：没有对比参照，judge 倾向给高分。

#### Pairwise win/tie/lose 失败

做法：candidate 和 teacher report 比较，输出 lose/tie/win。

问题：

```text
早期模型多数输给 teacher，分数塌缩到 0。
```

最终采用连续 pairwise score + 归一化。

启发：

```text
开放任务 reward 既不能太宽松，也不能太苛刻；
需要可区分、稳定、不过度离散的 scoring 设计。
```

## 20. 论文最重要的工程思想

### 20.1 合成任务必须同时生成评价器

Quest 不是只生成问题和答案，而是生成：

```text
任务 + rubric tree + evaluation protocol
```

这是可训练闭环的关键。

如果只有合成问题，没有可自动评价协议，RL 很难做。

### 20.2 Rubric Tree 是数据、评测、RL 的统一语言

同一个 rubric tree 用于：

- 合成问题；
- 过滤任务；
- 生成评价脚本；
- SFT trajectory 筛选；
- RL reward；
- benchmark 评价。

这减少了训练目标和评测目标不一致。

### 20.3 Context State 比 raw context 更重要

长程 Agent 的关键不是拥有无限上下文，而是拥有：

```text
结构化、可更新、能区分确定/不确定/错误的信息状态。
```

这和业务预测 Agent 非常一致，因为预测中经常有：

- 已确认事实；
- 传闻或低可信信息；
- 需要继续验证的关键变量；
- 与 baseline 冲突的信号。

### 20.4 Session-level training 是长轨迹训练的关键技巧

完整轨迹训练会受上下文长度和显存限制。

Session-level training 允许：

```text
训练短上下文 session，推理时组合成超长轨迹。
```

这对任何长程工具 Agent 都实用。

### 20.5 RL 基础设施比算法同样重要

Quest 的 RL 成功依赖：

- 缓存；
- 异步 rollout；
- 异步 evaluation；
- fallback 模型；
- timeout；
- queue；
- session 去重；
- 工具成本控制。

DeepResearch RL 不是写一个 reward 函数就能跑。

## 21. 批判性阅读

### 21.1 “Fully Synthetic” 并不等于完全低成本或完全独立

Quest 的任务是全合成，但合成过程强依赖：

- Claude Sonnet 4.5；
- GPT-5 / GPT-5.2 / GPT-5-mini；
- Tongyi DeepResearch；
- Serper；
- Jina；
- Google Trends；
- Google Scholar。

因此更准确地说：

```text
没有人工逐条标注，但使用了多个强闭源模型和外部工具自动生成、筛选、评价。
```

如果要在企业内部复现，需要替换这些组件。

### 21.2 Objective evaluation script 仍有错误

人工抽检 50 个脚本中：

- 2 个不可执行；
- 6 个 rubric 相关错误。

这说明自动评价脚本不能完全信任。

在高风险业务场景中，必须：

- 增加单元测试；
- 对 evaluator 做人工抽检；
- 对高价值样本人工复核；
- 记录 evaluator 版本；
- 避免 evaluator 漏判。

### 21.3 Open-ended judge 仍然有主观性

即使用 pairwise normalization，也无法完全消除：

- judge 偏好；
- reference report 质量影响；
- 评分维度权重偏差；
- 候选报告风格偏差；
- 复杂报告中的多维 trade-off。

所以 open-ended 结果更适合看趋势，不应作为唯一业务验收标准。

### 21.4 数据合成有分布塑形效应

论文自己也发现：

```text
训练数据合成 recipe 决定模型擅长什么。
```

这既是优点也是风险。

如果你的业务预测 Agent 训练数据过度偏向某类任务，会导致：

- 对其他业务场景泛化差；
- 工具调用习惯过拟合；
- 在受限工具 benchmark 中误调用工具；
- 对真实用户问题不鲁棒。

### 21.5 RL 可能带来 alignment tax

Quest 的 RL 提升 open-ended 报告，但略降 HLE/GAIA。

说明：

```text
强化某类 DeepResearch 行为可能牺牲部分专家推理或事实问答能力。
```

业务预测 Agent 也要注意：

- RL 优化成本可能让模型少查关键证据；
- RL 优化格式可能降低推理深度；
- RL 优化校准可能让模型过度保守；
- RL 优化业务收益可能牺牲公平或合规。

## 22. 对业务预测 Agent 的启发

你要做的业务型预测 Agent 和 Quest 有很强对应关系，但必须加入 Point-in-Time 和 outcome。

### 22.1 Rubric Tree 可以用于预测任务定义

每个业务预测任务可以有一棵 Forecast Rubric Tree。

例如“预测某产品下季度销售额是否同比增长超过 15%”：

```text
Root: 预测质量
  -> 标签定义
      -> 明确 forecast_time
      -> 明确 deadline
      -> 明确同比增长计算方式
  -> 内部证据
      -> 历史销售趋势
      -> 库存约束
      -> 渠道促销计划
  -> 外部证据
      -> 行业需求变化
      -> 竞品供给/促销
      -> 政策或宏观影响
  -> 预测推理
      -> 支持证据和反证都覆盖
      -> 与 baseline 模型差异解释
      -> 概率不能过度自信
  -> 输出格式
      -> prediction/probability/confidence/risk_factors 完整
```

这棵树可以用于：

- 构造训练样本；
- 质检 Agent 轨迹；
- 生成 DPO/RL reward；
- 给业务专家审阅；
- 回流错误分析。

### 22.2 Objective task 对应可回测预测

Quest 的 objective tasks 可自动验证。

业务预测中的对应物是：

```text
历史预测任务 + 真实 outcome + proper scoring rule
```

差异：

| Quest objective | 业务预测 objective |
|---|---|
| 答案可由网页当前事实验证 | 答案在未来发生后验证 |
| Python script 检查 answer 是否满足 constraints | outcome_lookup 计算真实标签 |
| rubric score 作为 reward | Log Loss / Brier / MAE / NDCG 作为 reward |
| 禁止 hard-coded answer | 禁止未来泄漏和标签泄漏 |

### 22.3 Open-ended task 对应预测报告

业务预测 Agent 不只输出 yes/no，还要输出预测报告：

- 为什么这么判断；
- 关键证据；
- 反证；
- 置信度；
- 风险因素；
- 哪些新信息会改变判断；
- 建议业务动作。

这部分可以借鉴 Quest open-ended rubric：

| Quest 维度 | 业务预测改造 |
|---|---|
| Instruction Following | 是否按预测 schema 输出 |
| Comprehensiveness | 是否覆盖关键数据源和变量 |
| Readability | 是否业务可读、可审计 |
| Insight | 是否有因果解释、场景分析、决策价值 |
| Citation Grounding | 是否引用 evidence_id、数据表、网页快照 |
| Calibration | 业务预测新增维度，概率是否合理 |
| Leakage Control | 业务预测新增维度，是否使用未来信息 |

### 22.4 Context State 非常适合预测 Agent

预测任务中可以维护类似：

```json
{
  "information_state": {
    "trusted": [
      {"claim": "截至 forecast_time，产品 A 近 3 月同比增速为 8%、11%、13%", "source": "sales_dw"}
    ],
    "untrusted": [
      {"claim": "竞品已经完全停产", "reason": "只有社交媒体传闻，未被公告确认"}
    ],
    "uncertain": [
      {"claim": "4 月促销可能提高转化", "need": "查询历史类似促销转化率"}
    ]
  }
}
```

这比普通 RAG summary 更适合预测，因为预测关键在于不确定性管理。

### 22.5 Session-level training 可用于长程预测轨迹

业务预测 Agent 可能查很多工具：

- 内部数据库；
- 财报；
- 新闻；
- 行情；
- 研报；
- 代码计算；
- baseline 模型；
- 结果回流。

完整轨迹很长，session-level training 可以降低训练成本。

### 22.6 Quest 的 reward 公式可改造成预测 reward

Quest：

```text
R = 0.75 * rubric + 0.25 * min(fact, rubric)
```

业务预测可改为：

```text
R = 0.55 * outcome_score
  + 0.15 * calibration_score
  + 0.15 * evidence_score
  + 0.10 * process_rubric_score
  + 0.05 * format_score
  - leakage_penalty
  - cost_penalty
```

其中：

- outcome_score：Brier / Log Loss / MAE；
- calibration_score：概率桶校准；
- evidence_score：证据是否支持 claim；
- process_rubric_score：工具规划、反证处理等；
- format_score：JSON 可解析；
- leakage_penalty：未来泄漏强惩罚；
- cost_penalty：工具和 token 成本。

## 23. 可复现的 Quest-lite 路线

如果要借鉴 Quest，但资源有限，可以做简化版。

### 23.1 数据合成 lite

先不要自动生成 8K 全量任务。

建议：

```text
1. 人工定义 3-5 个业务任务模板
2. 每个模板生成 100-500 条历史任务
3. 每个任务生成 Forecast Rubric Tree
4. 用规则 + 小模型检查 rubric 是否泄漏
5. 用真实 outcome 自动评分
```

### 23.2 Context management lite

先实现：

```json
{
  "trusted": [],
  "untrusted": [],
  "uncertain": [],
  "next_actions": []
}
```

不必一开始训练 Context Condenser，可以用强模型/prompt 生成，再逐渐蒸馏到 Qwen3.6-35B。

### 23.3 SFT lite

数据配比：

| 样本类型 | 比例 |
|---|---:|
| 任务解析 + rubric tree | 15% |
| 工具调用轨迹 | 35% |
| Context State 更新 | 20% |
| 最终预测 JSON | 20% |
| 错误修复/反思 | 10% |

### 23.4 RL lite

先用离线 historical replay。

不要直接在线 RL。

流程：

```text
历史任务 -> 按 forecast_time 回放工具 -> 多 rollout -> 真实 outcome reward -> GRPO
```

加入：

- evidence reward；
- leakage penalty；
- cost penalty；
- format reward。

## 24. Quest 与 RubricEM 的互补

这两篇新增论文放在一起看，非常有价值。

| 维度 | Quest | RubricEM |
|---|---|---|
| 核心问题 | 如何合成可训练、可评价的 DeepResearch 任务 | 如何在开放长报告任务中做有效 RL credit assignment |
| Rubric 形式 | Rubric Tree | Stagewise Rubrics + Rubric Bank |
| 数据 | 完全合成任务，objective + open-ended | 沿用 DR Tulu 数据，SFT teacher distillation |
| 上下文 | Context State / Context Condenser | Stage scaffold + reflection memory |
| RL | GRPO，scalar reward 给 rollout/session | SS-GRPO，stagewise reward 给阶段 token |
| Memory | 结构化 context state | Reflection rubric bank |
| 工程重点 | 缓存、异步 evaluation、session-level training | 异步 reflection branch、evolving rubric buffer |

对业务预测 Agent 的组合方案：

```text
用 Quest 的 Rubric Tree 构造预测任务和评价协议；
用 Quest 的 Context State 管理长程证据；
用 RubricEM 的 stage scaffold 和 SS-GRPO 做过程级 credit；
用 RubricEM 的 reflection bank 做 outcome-aware 错误经验复用。
```

## 25. 最适合重点借鉴的模块

### 25.1 必须借鉴

- Rubric Tree 任务表示；
- Context State 三分法；
- Session-level training；
- 搜索/访问缓存；
- SFT trajectory 评分过滤；
- reward 中加入 fact/evidence checking。

### 25.2 V1 再借鉴

- 大规模自动任务合成；
- Python evaluation script 自动生成；
- 异步 evaluation actors；
- 多模型 fallback；
- MT context summarization；
- relevant information extraction mid-training。

## 27. 最终理解

Quest 这篇论文最值得记住的不是某个 benchmark 数字，而是一套完整开源 DeepResearch Agent 工程范式：

```text
先自动合成真实复杂任务，
同时生成 rubric tree 和 evaluation protocol，
再用上下文状态管理支持长程工具交互，
再用 MT 训练模型理解长上下文和网页噪声，
再用 SFT 学工具轨迹，
最后用 rubric-tree reward 和 fact-checking reward 做 RL。
```

它证明：

```text
高质量合成任务 + 可自动评价协议 + 结构化上下文管理 + 分阶段训练，
可以让 open-weight 模型接近甚至部分超过 proprietary DeepResearch 系统。
```

对你的业务预测 Agent 来说，Quest 的最大启发是：

1. **每个预测任务都要有结构化评价树**，否则训练和评测目标会混乱；
2. **上下文不是越长越好，而是要维护 trusted/untrusted/uncertain 状态**；
3. **合成数据必须同时合成 evaluation protocol**，业务预测中就是 outcome 计算规则和防泄漏规则；
4. **SFT 前最好做轻量 Agentic Mid-training**，尤其是 context summarization 和 information extraction；
5. **RL reward 要把任务完成和证据 grounding 绑定**，不能让模型靠漂亮引用或漂亮解释骗分；
6. **DPO 对长报告/复杂预测不一定稳**，要谨慎构造偏好对；
7. **小模型可做事实检索子 Agent，大模型负责复杂综合和最终预测**。

如果把 Quest 和 RubricEM 合并到你的项目中，推荐的最终训练路线是：

```text
Forecast Rubric Tree 数据构造
-> Point-in-Time Evidence Snapshot
-> Context State / Context Condenser
-> Agentic MT
-> Stage-aware SFT
-> Rubric/Evidence/Outcome 评测
-> DPO 或偏好过滤
-> Stagewise RLVR / GRPO
-> Outcome-aware Reflection Bank
-> 影子上线和真实结果回流
```

这会比单纯“搜索 + SFT + RL”更稳健，也更适合业务预测这种既需要 DeepResearch 又需要真实结果校验的 Agent。
