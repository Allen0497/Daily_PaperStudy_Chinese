## 1. 一句话总结

RubricEM 的核心思想是：**对于 DeepResearch 这类没有标准答案、输出是长报告、轨迹很长且工具调用很多的任务，不应该只用最终答案的 LLM Judge 分数做 RL，而应该把“rubric 评分标准”贯穿到 Agent 的规划、检索、审查、回答、奖励分配和经验记忆中；再通过阶段化 GRPO 与反思型 Meta-Policy，让模型学会更稳定地做长程研究。**

更短地说：

```text
RubricEM = rubric-guided scaffold + stage-structured GRPO + reflection meta-policy + rubric bank
```

它解决的问题不是“如何让模型检索到一个可验证答案”，而是：

```text
当任务没有唯一标准答案、只能用多维 rubric 判断好坏时，RL 如何给长程 Agent 分配信用，
并把一次尝试中的经验转化为下次可复用的指导？
```

## 2. 论文定位

### 2.1 它和前面几篇 DeepResearch 论文的关系

这篇论文和之前目录中的几篇论文关系非常紧密：

| 论文 | 主要关注点 | RubricEM 的关系 |
|---|---|---|
| MiroThinker | Interactive Scaling、工具交互、SFT/DPO/RL | RubricEM 进一步研究长程 RL 的信用分配问题 |
| MiroThinker-1.7 & H1 | 阶段化能力、Local/Global Verifier、Heavy Reasoning | RubricEM 也强调阶段结构和过程级判断，但用 rubric 做统一接口 |
| REDSearcher | 可控任务合成、证据分散、模拟环境 | RubricEM 不重点做数据合成，而重点做 open-ended RL 算法 |
| Tongyi DeepResearch | Mid-training/SFT/RL 全流程训练 | RubricEM 是对 RL 阶段的算法级增强 |
| S1-DeepResearch | 多维轨迹构造和验证 | RubricEM 把多维验证进一步用于 RL credit assignment 和经验记忆 |
| DR Tulu | Open-ended long-form DeepResearch RL | RubricEM 最接近 DR Tulu，并在其基础上引入 stagewise credit 和 reflection meta-policy |

RubricEM 的关键定位是：

```text
不是提出一个新的搜索工具；
不是主要提出一个新的数据合成系统；
不是只做 prompt scaffold；
而是提出一种让“rubric”同时服务于 Agent 执行、Judge 评分、RL 奖励和经验记忆的训练框架。
```

### 2.2 它要解决的核心难点

DeepResearch 长报告任务和数学题、代码题、短问答不一样：

| 任务类型 | Reward 是否容易构造 | 典型 reward |
|---|---|---|
| 数学题 | 容易 | 最终答案是否等于标准答案 |
| 代码题 | 容易 | 单元测试是否通过 |
| 多跳问答 | 中等 | exact match / F1 / 引用是否命中 |
| DeepResearch 长报告 | 困难 | 内容覆盖、证据质量、结构、洞察、可读性、引用、反证处理 |

因此 DeepResearch RL 面临三个问题：

1. **没有可验证标准答案**：长报告通常没有唯一正确答案，只能判断“更好/更差”；
2. **反馈延迟且粗糙**：如果只给最终报告一个分数，模型不知道是计划错、搜索错、证据错、审查错，还是写作错；
3. **经验难复用**：传统 RL 更新参数，但不会显式记录“这类任务下次应该注意什么”。

RubricEM 的回答是：

```text
用 rubric 估计任务的隐含结构：什么重要、哪个阶段该负责、什么经验值得记住；
再用这些 rubric 引导 policy、judge、reward 和 memory 一起演化。
```

## 3. 核心贡献

论文的核心贡献可以拆成六点。

### 3.1 把 rubric 从“最终评分表”升级为“全流程共享接口”

传统做法：

```text
Agent 先完成答案
Judge 再用 rubric 给最终答案打分
RL 用这个最终分数更新模型
```

RubricEM 的做法：

```text
Agent 一开始就生成 rubric
Agent 按 rubric 规划和检索
Judge 按 stage-specific rubric 评价每个阶段
Meta-policy 把 judged trajectory 总结成 reflection
Reflection 写入 rubric bank，影响未来任务
```

这里的 rubric 同时扮演：

- 任务理解工具；
- 搜索计划目标；
- 证据检查清单；
- 最终答案标准；
- 过程奖励标准；
- 经验记忆格式。

这就是论文标题中 “Rubric-guided Policy Decomposition” 的含义。

### 3.2 提出四阶段结构化推理脚手架

RubricEM 把长程研究轨迹拆成四个阶段：

```text
Plan -> Research -> Review -> Answer
```

每个阶段都有不同职责：

| 阶段 | 作用 |
|---|---|
| Plan | 理解问题、生成 rubric、制定 research plan |
| Research | 多轮调用工具、收集证据、更新状态和计划 |
| Review | 将证据映射回 rubric，检查是否满足标准，形成写作计划 |
| Answer | 生成带引用的最终长报告 |

这不是简单格式约束，而是为了让模型在不同阶段采用不同策略。

### 3.3 提出 Stage-Structured GRPO

普通 GRPO 做法：

```text
一个 rollout 得到一个最终分数
这个分数广播给整条轨迹所有 token
```

问题：如果最终报告分数低，模型不知道应该惩罚哪个阶段。

SS-GRPO 做法：

```text
分别给 Plan、Research、Review、Answer 四个阶段打分
每个阶段 token 使用该阶段的 advantage
同时加入下游阶段影响，反映早期阶段对最终结果的贡献
```

因此它提供了更密集、更语义化的 credit assignment。

### 3.4 提出 Reflection Meta-Policy

RubricEM 不只训练“做任务的 policy”，还训练“从做过的任务中总结经验的 meta-policy”。

流程：

```text
完成任务 rollout
Judge 给 trajectory 和各阶段打分
共享 backbone 生成多个 reflection candidate
Judge 判断哪个 reflection 更有用
用 reflection reward 更新模型
最佳 reflection 写入 rubric bank
未来相似任务检索这些 reflections
```

这让模型不仅通过参数学习，也通过文本记忆学习。

### 3.5 提出 Rubric Bank

Rubric Bank 是一个自然语言经验库，存储：

- 已完成任务的问题；
- 反思得到的 rubric；
- 可迁移的 takeaways；
- 对下次尝试有帮助的策略。

它支持两种使用方式：

| 模式 | 含义 |
|---|---|
| Cross-episode transfer | 新问题检索相似历史问题的经验 |
| Within-episode refinement | 同一个问题第二次尝试时检索上次失败/成功经验 |

### 3.6 实验显示小模型也能做强长报告研究

RubricEM-8B 在 4 个长报告研究 benchmark 上达到 open model 中很强的结果：

- HealthBench；
- ResearchQA；
- DeepResearchBench；
- ResearchRubrics。

它用 8B backbone 和 1400 个 RL steps，平均分达到 55.5，超过 DR Tulu-8B-RL、Tongyi DeepResearch-30B-A3B 等 open baseline，并接近部分 proprietary deep research 系统。

## 4. 为什么叫 RubricEM

论文把 RubricEM 解释为一种 EM-inspired 思路。

EM 算法通常包含：

```text
E-step：估计隐变量
M-step：在估计的隐变量下优化参数
```

RubricEM 的类比是：

```text
E-like：用 rubric 估计开放任务的隐含结构
M-like：在 rubric 条件下优化 task policy 和 reflection meta-policy
```

这里的隐含结构包括：

- 这个研究任务到底看重什么；
- 哪些阶段对成功负责；
- 哪些失败模式需要惩罚；
- 哪些经验值得写入记忆；
- 哪些 criteria 能区分好坏轨迹。

因此 RubricEM 不是严格的传统 EM 算法，而是借用了“先估计结构，再优化策略”的思想。

## 5. 问题形式化

论文把 DeepResearch Agent 形式化为：

```text
query q ~ D
agent 和 tool environment T 交互
trajectory τ = (a1, o1, ..., aT, oT)
```

其中：

| 符号 | 含义 |
|---|---|
| `q` | 用户研究问题 |
| `D` | 问题分布 |
| `T` | 工具环境 |
| `a_t` | Agent 在第 t 轮的输出，可以是文本，也可以是工具调用 |
| `o_t` | 工具返回结果，如果没有工具调用则为空 |
| `h_t` | 当前历史上下文，包括问题、之前动作和工具结果 |
| `π_θ` | 语言模型 policy |
| `τ` | 一整条研究轨迹 |

Agent 每一步从 policy 中采样：

```text
a_t ~ π_θ(a_t | h_t)
```

最终生成一个基于证据的长报告。

这个形式化强调：

```text
DeepResearch 不是单轮生成，而是长程工具交互轨迹。
RL 要优化的是整条轨迹，而不只是最终 answer token。
```

## 6. Structured Reasoning Scaffold 详解

### 6.1 为什么需要 stage structure

如果没有 stage structure，一条长轨迹只是：

```text
text -> tool call -> observation -> text -> tool call -> observation -> ... -> answer
```

模型需要从局部上下文猜测“现在该做什么”。

同样一句话或同样一个局部状态，在不同阶段的最佳动作可能完全不同：

| 当前情境 | 如果处于 Plan 阶段 | 如果处于 Research 阶段 | 如果处于 Review 阶段 | 如果处于 Answer 阶段 |
|---|---|---|---|---|
| 发现信息不足 | 制定检索目标 | 调用工具补证据 | 标记 gap | 降低结论强度或声明限制 |
| 有多个来源冲突 | 预设验证策略 | 找权威来源 | 判断证据等级 | 在答案中说明分歧 |
| 证据很多 | 决定优先级 | 停止重复搜索 | 组织结构 | 写成连贯报告 |

论文用一个理论结论说明：如果同一个压缩状态 `c` 下，不同阶段 `z` 的最优动作不同，那么能看到阶段标签的 policy 价值严格高于看不到阶段标签的 flat policy。

通俗解释：

```text
“我现在是在规划、搜索、审查还是写答案”这个信息本身有价值。
没有这个信息，模型容易把搜索阶段做成写作阶段，把审查阶段做成继续搜索。
```

### 6.2 四阶段结构

RubricEM 的轨迹结构是：

```text
<structured_plan>
  <deep_analysis>...</deep_analysis>
  <rubric>...</rubric>
  <research_plan>...</research_plan>
</structured_plan>

<call_tool>...</call_tool>
<tool_output>...</tool_output>

<state_evaluation>...</state_evaluation>
<call_tool>...</call_tool>
...

<review>
  <rubric_review>...</rubric_review>
  <writing_plan>...</writing_plan>
</review>

<answer>...</answer>
```

### 6.3 Plan 阶段

Plan 阶段包含三部分。

#### 6.3.1 Deep Analysis

分析用户的：

- 显式需求；
- 隐式需求；
- 缺失变量；
- 潜在路障；
- 检索难度；
- 推理难度；
- 输出格式需求。

例如用户问：

```text
How do sleep patterns affect cognitive decline in aging?
```

一个好的 deep analysis 不会只说“搜索睡眠和认知下降”，而会识别：

- 需要区分相关性和因果性；
- 需要区分睡眠时长、睡眠时间、慢波睡眠等不同因素；
- 需要避免混淆普通年龄相关记忆衰退和阿尔茨海默病；
- 需要找机制证据和纵向研究，而不是只找横截面相关性。

#### 6.3.2 Rubric

Agent 自己生成 answer 的评分标准。

Rubric 包含：

| 类别 | 作用 |
|---|---|
| Knowledge Checklist | 必须找到哪些事实、定义、比较、数据点 |
| Analytical Criteria | 最终答案必须完成哪些分析和综合 |
| Negative Constraints | 最终答案必须避免哪些错误 |

这一步非常关键，因为它把“任务成功标准”显式化。

#### 6.3.3 Research Plan

根据 rubric 制定工具调用计划：

- 先搜什么；
- 后搜什么；
- 如果初始证据不充分，如何 fallback；
- 哪些信息是必须有的；
- 什么时候可以停止。

论文强调：规划深度要随任务复杂度自适应。

```text
简单任务不应过度规划；复杂任务必须做条件式、多步规划。
```

### 6.4 Research 阶段

Research 阶段是循环：

```text
tool call -> tool output -> state evaluation -> next tool call or revise plan
```

每次工具返回后，Agent 要做 `state_evaluation`：

- 新证据满足了哪些 rubric 项；
- 还有哪些 rubric 未满足；
- 证据是否冲突；
- 是否需要换搜索方向；
- 是否已经足够进入 Review。

Research 阶段允许 in-place plan revision。也就是说，如果最初 plan 错了，Agent 可以更新：

- deep analysis；
- rubric；
- research plan。

这比固定 ReAct 更灵活。

### 6.5 Review 阶段

Review 是最终回答前的强制自审。

包含两部分：

| 子模块 | 作用 |
|---|---|
| `rubric_review` | 将已收集证据逐项映射回 rubric，检查满足情况 |
| `writing_plan` | 形成最终写作结构、中心论点、段落安排和引用映射 |

Review 的意义：

1. 防止证据不足时过早回答；
2. 防止最终答案脱离一开始的任务标准；
3. 让长报告有结构，而不是散乱堆砌来源；
4. 为 Answer 阶段提供明确蓝图。

### 6.6 Answer 阶段

Answer 阶段生成最终长报告。

要求：

- 遵循 writing plan；
- 满足 rubric；
- 对非平凡事实使用 inline citation；
- 按任务要求输出 exact / short-form / long-form；
- 不能模拟工具结果；
- 不能在第一轮直接 answer。

## 7. Scaffold 不是格式工程，而是结构先验

这篇论文很重要的一点是：它把 scaffold 当成训练结构先验，而不是 prompt trick。

如果只是加 XML 标签，意义有限；真正的作用是：

```text
1. 给 policy 明确决策模式；
2. 给 judge 明确评分单位；
3. 给 RL 明确 advantage 归因范围；
4. 给 reflection 明确总结对象；
5. 给 rubric bank 明确记忆格式。
```

因此 scaffold 是整个 RubricEM 的基础。如果没有阶段边界，就无法做 stagewise reward，也很难生成阶段化 reflection。

## 8. SFT Distillation 详解

### 8.1 为什么需要 SFT

SS-GRPO 和 Reflection Meta-Policy 都要求模型能稳定输出：

- `<structured_plan>`；
- `<rubric>`；
- `<research_plan>`；
- `<call_tool>`；
- `<state_evaluation>`；
- `<review>`；
- `<answer>`。

如果 base model 不会遵守这些结构，RL 会非常不稳定。

因此 RubricEM 先做 SFT，把结构化 scaffold 注入 policy。

### 8.2 Teacher 模型

论文使用：

```text
Teacher: Gemini-3.1-Pro
Student: Qwen3-8B
```

Teacher 被要求生成 stage-structured trajectory。

### 8.3 数据过滤

原始 teacher trajectory 不一定合格，所以论文进行 rejection sampling。

过滤掉的问题包括：

- stage boundary 错误；
- 工具调用语法错误；
- citation 格式错误；
- grounding 不足；
- 过早输出 answer；
- 没有真实工具调用；
- 伪造工具输出；
- 没有按 rubric 做 review。

### 8.4 Tool output masking

SFT 时对 `<tool_output>` 做 span masking。

含义：

```text
模型不需要学习生成工具返回内容；
模型只学习生成自己的计划、工具调用、状态评估、审查和答案。
```

这对工具 Agent 训练很重要，否则模型会学会“编造 observation”。

### 8.5 SFT 超参

论文给出的 SFT 配置：

| 项目 | 值 |
|---|---|
| Base model | Qwen3-8B |
| 框架 | LLaMA-Factory + DeepSpeed ZeRO-3 |
| Epochs | 5 |
| LR | 4e-5 |
| Scheduler | Cosine + 10% warmup |
| Effective batch size | 128 |
| Max sequence length | 16,384 |
| Precision | BF16 |
| Weight decay | 0 |
| Tool output masking | Span masking on tool output |
| GPU | 8 × H100 80GB |

## 9. Stage-Structured GRPO 详解

### 9.1 普通 GRPO 的问题

普通 long-horizon RL 通常做：

```text
对同一个 query 采样 n 条 rollout
每条 rollout 得到一个最终 reward
在 group 内标准化 reward，得到 advantage
整条轨迹所有 token 使用同一个 advantage
```

问题：

```text
最终答案差，不代表每个阶段都差。
可能是 Plan 好但 Research 搜错；
也可能 Research 好但 Answer 写坏；
也可能 Answer 好但 citation 差。
```

如果把最终 reward 广播给所有 token，就会误伤好阶段，也会放过坏阶段。

### 9.2 SS-GRPO 的基本变量

对 query `q` 采样 `n` 条 rollout：

```text
{τ_i}_{i=1}^n ~ π_θ(. | q)
```

每条 rollout 被分成 `K=4` 个 stage：

```text
k = 1: Plan
k = 2: Research
k = 3: Review
k = 4: Answer
```

定义：

| 符号 | 含义 |
|---|---|
| `B_{i,k}` | 第 i 条 rollout 中第 k 个 stage 的 token 集合 |
| `R_{i,k}` | Judge 给第 i 条 rollout 第 k 个 stage 的 rubric 分数 |
| `Λ` | stage 依赖矩阵 |
| `G^Λ_{i,k}` | 第 i 条 rollout 第 k 个 stage 的 stage return |
| `A_{i,k}` | 第 i 条 rollout 第 k 个 stage 的 normalized advantage |

### 9.3 Stage return

SS-GRPO 不只是用当前 stage 分数，也考虑下游 stage。

公式思想：

```text
G^Λ_{i,k} = sum_{j=k}^K λ_{k,j} R_{i,j}
```

含义：

- Plan 阶段应该对后续 Research、Review、Answer 有贡献；
- Research 阶段应该对 Review 和 Answer 有贡献；
- Review 阶段应该对 Answer 有贡献；
- Answer 阶段只用自身分数。

论文使用的 Λ 矩阵是：

```text
[1.0, 0.4, 0.6, 0.8]
[0.0, 1.0, 0.4, 0.8]
[0.0, 0.0, 1.0, 0.8]
[0.0, 0.0, 0.0, 1.0]
```

解释：

| 阶段 | 直接分数 | 下游影响 |
|---|---|---|
| Plan | 1.0 × Plan | 还接收 Research/Review/Answer 的部分反馈 |
| Research | 1.0 × Research | 还接收 Review/Answer 的部分反馈 |
| Review | 1.0 × Review | 还接收 Answer 的部分反馈 |
| Answer | 1.0 × Answer | 无下游 |

这样做的原因：早期阶段如果好，通常会让后续阶段更好；但不能完全把后续好坏都归因给早期阶段。

### 9.4 Stagewise advantage

每个 stage 在同一 query 的 rollout group 内单独标准化：

```text
A_{i,k} = (G^Λ_{i,k} - mean_i(G^Λ_{i,k})) / (std_i(G^Λ_{i,k}) + ε)
```

关键点：

```text
Plan token 用 Plan advantage；
Research token 用 Research advantage；
Review token 用 Review advantage；
Answer token 用 Answer advantage。
```

这比 terminal reward broadcast 更精细。

### 9.5 SS-GRPO objective

SS-GRPO 使用类似 PPO clipping 的目标：

```text
L = - average over rollout, stage, token of
    min(ρ * A, clip(ρ, 1-η, 1+η) * A)
    + β * KL(π_θ || π_ref)
```

其中：

```text
ρ = π_θ(a_t | h_t) / π_old(a_t | h_t)
```

它仍然是 critic-free，因为：

- stage score 来自不断变化的 judge rubric；
- rollout 很长且工具调用昂贵；
- 再训练一个 critic 会显著增加复杂度和不稳定性。

### 9.6 为什么 stage return 可能更好

论文给出理论分析：stagewise credit 有一个 trade-off。

好处：

```text
恢复终端 reward 遗漏的过程信息。
```

代价：

```text
引入中间 judge 的噪声和偏差。
```

当“恢复的中间信号”大于“judge 噪声造成的误差”时，stagewise credit 更接近理想梯度。

通俗理解：

```text
如果 judge 能比较可靠地区分计划好坏、搜索好坏、审查好坏，
那么阶段化 reward 会比一个最终分数更有用。
如果 judge 很差，阶段化 reward 可能反而引入噪声。
```

## 10. Stagewise Evolving Rubric Judge

### 10.1 为什么不能只用固定 rubric

固定 rubric 的问题：

- 可能太泛，不区分当前 query 的真实难点；
- 随着 policy 变强，旧 rubric 可能不再有区分度；
- 对不同阶段的失败模式不敏感；
- 容易奖励格式，而不是实质。

RubricEM 的 judge 会维护每个阶段的 rubric buffer，并动态更新。

### 10.2 Rubric buffer

每个 query、每个 stage 都有 rubric buffer：

```text
Plan rubric buffer
Research rubric buffer
Review rubric buffer
Answer rubric buffer
```

其中包含：

- persistent rubrics：长期保留的标准；
- active rubrics：动态生成、会被替换的标准。

论文实验中的 active rubric cap：

| Stage | Active rubric cap |
|---|---:|
| Plan | 3 |
| Research | 2 |
| Review | 2 |
| Answer | 3 |

### 10.3 Adaptive rubric generation

每个 RL step：

1. 对同一个 query 采样多条 rollout；
2. Judge 对比这些 rollout；
3. 找出最能区分好坏的 stage-specific criteria；
4. 生成新的 positive / negative rubrics；
5. 加入对应 stage 的 buffer；
6. 删除区分度低的旧 active rubrics。

区分度用 score variance 衡量：

```text
如果某个 rubric 对所有 rollout 打分都差不多，它就不能提供有效训练信号，应被删除。
```

### 10.4 Positive 与 Negative rubric

Judge rubric 分两类：

| 类型 | 含义 | 打分 |
|---|---|---|
| Positive rubric | 希望出现的好行为 | 0/1/2 表示 absent/partial/full |
| Negative rubric | 希望避免的坏行为 | 0/1/2 表示 no flaw/partial flaw/full flaw，聚合时反转 |

例子：

| Stage | Positive rubric | Negative rubric |
|---|---|---|
| Plan | 识别隐含约束 | 只复述问题，不拆解任务 |
| Research | 搜索 query 精确且能 follow up | 重复搜索同一信息 |
| Review | 诚实指出证据 gap | 声称证据充分但实际缺失 |
| Answer | 综合清晰且引用可靠 | 堆砌来源或夸大结论 |

### 10.5 Anti-hack rules

论文特别强调，rubric 不能只奖励表面格式。

不好的 rubric：

- 只检查 XML tag 是否存在；
- 奖励坏计划的形式化执行；
- 过拟合某一条 trajectory 的措辞；
- 把自洽当成真实质量；
- 奖励不必要的复杂度；
- 惩罚基于证据的 plan revision。

好的 rubric 应该：

- 少而尖锐；
- 能区分 rollout 质量；
- 针对当前 query 的关键失败模式；
- 分阶段；
- 关注语义质量而不是格式。

### 10.6 批量与效率

论文训练中：

```text
每步 32 个 unique questions
每个问题 8 条 rollouts
共 256 条 trajectories
```

Rubric generation：

```text
32 calls / step，每个 question 一次
```

Scoring：

```text
256 calls / step，每条 trajectory 一次
```

使用 Gemini structured output + Pydantic JSON schema 保证输出结构。

## 11. Reflection Meta-Policy 详解

### 11.1 为什么需要 meta-policy

普通 RL 的经验利用方式：

```text
一次 rollout -> reward -> 参数更新
```

问题：

- 参数更新是隐式的；
- 不能在推理时显式告诉模型“上次这类任务哪里错了”；
- 对相似任务的迁移效率低；
- 长程研究中的失败经验很有语义价值，不应该被丢弃。

RubricEM 让模型额外学习：

```text
如何把一条 judged trajectory 总结成可复用的 reflection。
```

### 11.2 共享 backbone

RubricEM 中：

```text
Task Policy 和 Reflection Meta-Policy 共享同一个 backbone。
```

区别是输入和训练 token：

| Policy | 输入 | 输出 | 训练信号 |
|---|---|---|---|
| Task policy | query + memory + tools | research trajectory + answer | stagewise GRPO reward |
| Reflection meta-policy | query + raw trajectory | reflection rubrics + takeaways | reflection judge reward |

Reflection 训练时：

```text
trajectory 作为固定上下文；
只对 reflection tokens 反传。
```

### 11.3 Reflection candidate 生成

对一个 query，从 rollout group 中随机采样一条 trajectory。

然后生成多个 reflection candidates，例如 `m=8`。

Reflection 应该输出两类内容：

```text
<reflection_rubrics>
针对这类任务下次应该检查什么
</reflection_rubrics>

<reflection_takeaways>
1-4 条可迁移经验
</reflection_takeaways>
```

反思不是重写答案，也不是泛泛而谈，而是要：

- 找出最高杠杆的成功或失败点；
- 追溯到可见 trajectory；
- 给出下一次尝试可用的具体指导；
- 同时对相似问题有迁移价值。

### 11.4 Reflection judge

Judge 用 privileged information 给 reflection 打分。

输入包括：

- 原始 query；
- 原始 trajectory；
- stagewise rubric scores；
- evaluator justifications；
- reflection candidates。

评分维度包括：

| 维度 | 权重 | 含义 |
|---|---:|---|
| Diagnostic Accuracy | 0.4 | 是否准确识别主要强弱点和根因 |
| Specificity | 0.3 | 是否具体、可执行、针对当前问题 |
| Scope & Balance | 0.3 | 是否也能迁移到相似任务，且覆盖均衡 |

重要原则：

```text
Reflection 的分数评价的是“未来指导价值”，不是原 trajectory 本身的质量。
失败轨迹也可以产生高质量 reflection。
完美轨迹也可能产生低质量泛泛 reflection。
```

### 11.5 Rubric bank

每条 bank item 存储：

- question；
- query embedding；
- reflection rubrics；
- reflection takeaways；
- 可能的分数和时间步。

检索方式：

| 模式 | 检索方法 |
|---|---|
| Cross-episode | 用 Qwen3-Embedding-0.6B 计算 query embedding，FAISS top-k，相似问题默认 top-2 |
| Within-episode | 精确 question hash 匹配，检索同一问题上次 reflection |

Bank 持久化：

- 每 10 steps 保存；
- checkpoint 时保存；
- 使用 atomic write；
- resume 时和模型权重保持同一 global step。

### 11.6 两种经验复用

#### Cross-episode transfer

新问题开始时，检索相似历史问题：

```text
下面是类似问题的 rubrics 和 takeaways，请适配当前问题，不要照抄。
```

作用：让模型进行类比迁移。

#### Within-episode refinement

同一个问题再次尝试时，注入上一次反思：

```text
你曾经尝试过这个问题，下面是上次尝试的 rubrics 和 reflections，请避免过去错误。
```

作用：让模型做自我改进。

### 11.7 Windowed curriculum

为了支持 within-episode refinement，论文使用窗口式课程。

设窗口大小 `K=3`，一个窗口有 `2K=6` 步：

| Step | Phase | Data | Retrieval mode |
|---:|---|---|---|
| 1 | New | B1 fresh | Cross-episode |
| 2 | New | B2 fresh | Cross-episode |
| 3 | New | B3 fresh | Cross-episode |
| 4 | Repeat | B1 replay | Within-episode |
| 5 | Repeat | B2 replay | Within-episode |
| 6 | Repeat | B3 replay | Within-episode |

这样可以保证：

```text
第一次尝试后的 reflection 已经生成、评分、写入 bank，并至少完成一次 deferred training，
第二次遇到同一问题时可以检索到上次 reflection。
```

## 12. 异步训练架构

### 12.1 为什么需要异步

如果同步执行：

```text
rollout -> judge trajectory -> generate reflection -> judge reflection -> meta-policy update -> 下一步 rollout
```

训练会被 reflection 阶段阻塞。

DeepResearch rollout 本身已经很慢，因为包括：

- 多轮生成；
- 搜索 API；
- Semantic Scholar；
- Judge API；
- 长上下文。

再同步加 reflection，会导致 GPU 和 API 等待严重。

### 12.2 RubricEM 的三线程架构

论文使用三条并发线程：

| 线程 | 职责 |
|---|---|
| Main training thread | 执行 task-policy update 和 deferred reflection update |
| Inference thread | 用 vLLM 生成多轮工具调用 rollout |
| Data preparation thread | 并行调用 judge、生成 reflection、评分 reflection、准备 batch |

### 12.3 One-step deferred reflection

在第 `N` 步：

1. 生成第 `N` 步 task rollout；
2. Judge 给第 `N` 步 rollout 打 stagewise 分数；
3. 立即用这些分数做 SS-GRPO task-policy update；
4. 同时后台生成和评分第 `N` 步 reflection；
5. 第 `N+1` 步开始时，用第 `N` 步准备好的 reflection batch 做 meta-policy update。

这叫 one-step staleness。

优点：

```text
reflection training 几乎不增加 SS-GRPO 主循环 wall-clock 时间。
```

代价：

```text
meta-policy 使用的是落后一小步的经验，可能有轻微 stale。
```

## 13. RubricEM 算法总流程

可以把 Algorithm 1 简化为：

```text
输入：SFT policy πθ、reference policy、query dataset、tool env、judge、rubric bank

for each RL step:
    1. 从数据集中采样一批 query
    2. 从 rubric bank 检索 cross/within 经验
    3. 如果有上一步 reflection batch，先做 reflection meta-policy update
    4. 对每个 query 采样 n 条 tool-augmented rollouts
    5. Judge 对比 rollouts，生成 stage-specific rubrics
    6. 更新每个 stage 的 rubric buffer
    7. Judge 用 rubrics 给每条 trajectory 的每个 stage 打分
    8. 根据 Λ 计算 stage returns
    9. 对每个 stage 做 group normalization 得到 advantages
    10. 修剪低区分度 rubrics
    11. 异步启动 reflection generation 和 reflection judging
    12. 用 stage advantages 做 SS-GRPO task-policy update
    13. 收集完成的 reflection batch，供下一步训练

输出：trained policy + rubric bank
```

核心循环是两个耦合系统：

```text
Task loop: rollout -> stagewise judge -> SS-GRPO update
Reflection loop: judged trajectory -> reflection candidates -> judge -> meta-policy update -> rubric bank
```

## 16. 论文最重要的思想

### 16.1 Rubric 应该前置，而不是后置

传统 rubric 是最终评分工具。

RubricEM 认为：

```text
如果 rubric 定义了什么是好答案，Agent 就应该从一开始用它规划搜索。
```

这对业务预测尤其重要。比如预测客户流失，rubric 不应只在最后评分，还应一开始要求：

- 查历史行为；
- 查近期投诉；
- 查竞品活动；
- 查合同到期；
- 查行业周期；
- 评估反证；
- 输出概率校准。

### 16.2 长程 RL 的 reward 应分阶段

长程 Agent 的错误来自多个环节：

```text
问题理解 -> 工具选择 -> 查询构造 -> 证据筛选 -> 状态更新 -> 反证处理 -> 最终写作
```

只用最终 reward 太粗。

RubricEM 的 stagewise reward 提供了一个可落地方案。

### 16.3 Experience reuse 不应只是 prompt memory

很多 Agent 系统把 memory 当成推理时提示：

```text
检索一些历史经验，塞到 prompt 里。
```

RubricEM 进一步做：

```text
训练模型生成高质量 reflection；
用 judge reward 优化 reflection；
让 reflection 同时影响参数和文本记忆。
```

这让 memory 从“外部附加上下文”变成“训练目标的一部分”。

### 16.4 Judge 也应该演化

Judge 不更新参数，但 rubric buffer 会更新。

这相当于：

```text
随着 policy 变强，judge 的评价标准也会变得更能区分当前 rollout。
```

如果 judge rubric 一直不变，训练后期可能所有 rollout 都满足旧标准，reward 失去区分度。

## 17. 对业务预测 Agent 的启发

这篇论文对你要做的“业务型预测 Agent”非常有价值，但需要做预测任务改造。

### 17.1 可以直接借鉴的部分

| RubricEM 机制 | 业务预测 Agent 中的落地方式 |
|---|---|
| Plan/Research/Review/Answer scaffold | 改成 Forecast Plan / Evidence Research / Forecast Review / Prediction Output |
| Self-generated rubric | 预测前生成“判断标准和证据清单” |
| Stagewise reward | 对规划、检索、证据、预测、校准分别给 reward |
| Reflection meta-policy | 将预测失败/成功样本总结为 future forecasting lessons |
| Rubric bank | 建立业务场景经验库，如“销售预测”“风控预警”“舆情预测”的经验 |
| Cross-episode transfer | 新预测任务检索相似历史预测 case |
| Within-episode refinement | 高价值预测可多轮重跑并利用上轮反思 |
| Evolving rubric judge | 业务专家和模型共同维护阶段化评价标准 |

### 17.2 必须改造的部分

RubricEM 面向 open-ended long-form research，没有真实标准答案；业务预测有未来 outcome。

因此不能照搬：

```text
只用 LLM judge rubric reward
```

业务预测应该使用：

```text
最终 outcome reward + proper scoring rules + stagewise process reward + evidence reward + cost reward
```

推荐改造：

| RubricEM reward | 业务预测改造 |
|---|---|
| Answer rubric score | Log Loss / Brier / MAE / NDCG 等真实结果评分 |
| Stagewise rubric score | 规划质量、工具质量、证据覆盖、反证处理、泄漏检查 |
| Reflection reward | 是否准确总结预测错误根因，是否可迁移 |
| Rubric bank | 业务 case memory，必须带 outcome 和时间边界 |

### 17.3 预测型 stage scaffold 建议

可以设计为：

```text
<forecast_plan>
  <target_analysis>明确预测目标、窗口、标签和不确定性</target_analysis>
  <forecast_rubric>列出预测所需证据、反证和判断标准</forecast_rubric>
  <research_plan>计划调用哪些工具和数据源</research_plan>
</forecast_plan>

<evidence_research>
  工具调用、证据摘要、状态更新、反证搜索
</evidence_research>

<forecast_review>
  对照 rubric 检查证据是否充分
  检查时间泄漏
  检查概率是否过度自信
  检查和 baseline 的差异
</forecast_review>

<prediction>
  输出 probability、confidence、key evidence、risk factors、what would change my mind
</prediction>
```

### 17.4 业务预测 Reflection 示例

某次预测失败后，meta-policy 可生成：

```text
<reflection_rubrics>
对于季度销售预测，必须把“促销计划”拆成覆盖渠道、预算强度、实际库存、历史转化率，
不能只因为存在促销计划就上调概率。
</reflection_rubrics>

<reflection_takeaways>
1. 当历史增速接近阈值但行业需求偏弱时，概率应保持中等而非高置信。
2. 促销计划只有在库存和渠道覆盖同时满足时才是强正向证据。
3. 如果 baseline 模型和新闻信号冲突，应明确列出冲突并降低置信度。
</reflection_takeaways>
```

这些经验可以写入“销售预测 rubric bank”，供下次相似任务检索。

## 18. 批判性阅读

### 18.1 仍然强依赖 LLM Judge

RubricEM 的 reward 全部来自 rubric-based judge。

风险：

- Judge 偏好可能不稳定；
- Judge 可能被漂亮表达欺骗；
- Judge 对专业领域错误识别不足；
- Stagewise judge 增加了更多噪声入口；
- Rubric buffer 如果生成坏 criteria，可能强化错误方向。

论文也承认：更强 judge、judge ensemble、calibrated judge 是未来方向。

### 18.2 没有加入 citation/format/verifiable auxiliary reward

论文为了隔离 open-ended semantic reward，没有加入：

- format reward；
- citation reward；
- tool-use heuristic reward；
- grounding reward。

这让方法更纯粹，但实际生产系统中可能不够。

实际业务 Agent 应加入硬约束 reward：

- JSON 格式；
- 工具权限；
- 证据时间；
- citation 可追溯；
- 防泄漏；
- 成本。

### 18.3 Rubric bank 可能传播错误经验

如果一次 trajectory 被错误 judge 高分，reflection 也可能错误。

错误 reflection 写入 bank 后，会影响相似任务。

需要：

- bank item 置信度；
- 过期机制；
- 人工审计；
- 负例回收；
- 分业务域隔离；
- outcome 回流修正。

### 18.4 训练成本和工程复杂度高

RubricEM 每个 RL step 需要：

- 多条长 rollout；
- 工具调用；
- rubric generation；
- stagewise scoring；
- reflection generation；
- reflection scoring；
- FAISS retrieval；
- 异步训练。

这比普通 SFT/DPO 复杂很多。

MVP 不建议一上来完整复现 RubricEM。更合理是逐步采用：

```text
先 scaffold + SFT
再 stagewise verifier
再 reflection bank
最后 stagewise RL
```

### 18.5 Benchmark 仍是 LLM Judge 主导

长报告 benchmark 多依赖 LLM-as-a-Judge。

因此结果说明：

```text
RubricEM 更符合这些 benchmark 的 rubric judge 偏好。
```

但不完全等价于：

```text
RubricEM 在所有真实研究任务中都更可靠。
```

业务预测场景必须用真实 outcome 验证。

## 19. 适合复现的最小版本

如果资源有限，可以做 RubricEM-lite。

### 19.1 Stage 1：只做 scaffold SFT

目标：让模型稳定输出：

```text
Plan -> Research -> Review -> Answer
```

不做 RL。

验收：

- 格式正确率；
- 工具调用成功率；
- evidence mapping 质量；
- 最终输出合规率。

### 19.2 Stage 2：只做 stagewise evaluation

先不训练，只评测每条轨迹的：

- Plan score；
- Research score；
- Review score；
- Answer score。

用于错误分析。

### 19.3 Stage 3：做 reflection bank，但不训练 meta-policy

用 teacher 或 judge 自动生成 reflection，写入 bank。

推理时检索：

- 同业务场景经验；
- 同实体经验；
- 同错误类型经验。

观察是否提升。

### 19.4 Stage 4：做 stagewise DPO 或 reward reranking

在真正 RL 前，可以先构造偏好对：

```text
chosen = stagewise score 高且 outcome 更好的轨迹
rejected = stagewise score 低或高置信错误轨迹
```

用 DPO/IPO/ORPO 训练。

### 19.5 Stage 5：最后做 SS-GRPO

当以下条件满足再做：

- 环境稳定；
- stagewise judge 可靠；
- reward 与真实业务指标相关；
- rollout 成本可控；
- 有足够中等难度样本。

## 20. 对你当前 Qwen3.6-35B 项目的具体建议

你要做的是业务预测 Agent，基座是 Qwen3.6-35B。结合 RubricEM，建议：

### 20.1 训练路线调整

原路线：

```text
数据集 -> SFT -> DPO -> RL -> Verifier -> 上线
```

加入 RubricEM 后可改为：

```text
数据集
-> Forecast Rubric Tree / Rubric Schema 构造
-> Stage-aware SFT
-> Stagewise Verifier 训练
-> Reflection Bank 构建
-> DPO/IPO 偏好优化
-> Stagewise RLVR / GRPO
-> Outcome-aware Reflection 更新
```

### 20.2 数据格式增加 rubric 字段

每个预测任务应有：

```json
{
  "task_id": "...",
  "forecast_time": "...",
  "deadline": "...",
  "forecast_rubric": {
    "target_definition": [],
    "required_evidence": [],
    "counter_evidence": [],
    "calibration_rules": [],
    "negative_constraints": []
  }
}
```

### 20.3 RL reward 增加阶段分解

建议：

```text
Plan reward：是否明确预测窗口、标签、关键变量、工具计划
Research reward：是否找到关键证据、反证、baseline、结构化指标
Review reward：是否检查泄漏、证据冲突、概率校准、信息缺口
Prediction reward：真实 outcome 的 Log Loss/Brier/MAE/NDCG
Reflection reward：是否正确总结错误根因并能迁移
```

### 20.4 Reflection bank 增加 outcome-aware 信息

RubricEM 的 reflection 是 judge-aware。

业务预测应该是 outcome-aware：

```json
{
  "question_signature": "quarterly_sales_growth",
  "forecast_time": "2025-03-31",
  "prediction": 0.78,
  "outcome": 0,
  "error_type": "overconfidence_due_to_campaign_overweight",
  "reflection_rubric": "促销信号必须结合实际库存和历史转化率验证",
  "takeaways": [
    "不要把促销计划本身当成强证据",
    "当行业需求弱于阈值时应降低概率",
    "baseline 与 Agent 判断冲突时必须解释差异"
  ]
}
```

## 21. 术语速查

| 术语 | 含义 |
|---|---|
| Rubric | 任务评分标准/检查清单 |
| Scaffold | 强制 Agent 轨迹遵守的结构化流程 |
| Stage | 轨迹中的语义阶段，如 Plan/Research/Review/Answer |
| SS-GRPO | Stage-Structured GRPO，阶段化 advantage 的 GRPO |
| Stage return | 某阶段自身分数加下游阶段加权分数 |
| Evolving rubric | 随 policy 分布变化而更新的评价标准 |
| Rubric buffer | Judge 侧保存 stage-specific rubrics 的缓存 |
| Reflection meta-policy | 生成可复用反思经验的 policy |
| Rubric bank | Agent 侧保存历史 reflection 的记忆库 |
| Cross-episode transfer | 从相似历史问题检索经验 |
| Within-episode refinement | 同一问题再次尝试时使用上次反思 |
| One-step deferred training | reflection 更新滞后一轮，避免阻塞主 RL |
| Tool output masking | 训练时不对工具返回文本计算 loss |

## 22. 最终理解

RubricEM 最大的价值在于把 DeepResearch RL 中最难的三个问题串起来解决：

```text
开放任务如何定义好坏？ -> 用 rubric
长程轨迹如何分配信用？ -> 用 stagewise rubric reward
过去尝试如何变成经验？ -> 用 reflection meta-policy + rubric bank
```

它给出的范式是：

```text
先把长程研究任务显式分解成阶段；
再让每个阶段都围绕 rubric 行动；
再让 judge 用阶段 rubric 给出密集反馈；
再把被 judge 评价过的经验总结成可迁移反思；
最后让这些反思同时更新模型参数和文本记忆。
```

对业务预测 Agent 来说，这篇论文尤其重要，因为预测任务同样是：

- 多阶段；
- 多工具；
- 多证据；
- 多维质量标准；
- 需要反证；
- 需要从历史错误中学习。

但业务预测比 RubricEM 更进一步：最终有真实 outcome。因此最佳实践不是照搬纯 LLM Judge reward，而是：

```text
RubricEM 的阶段化过程奖励
+ 业务真实结果的 proper scoring reward
+ Point-in-Time 防泄漏
+ Outcome-aware reflection bank
```

这会比单纯 SFT 或单纯最终准确率 RL 更适合构建可靠的业务预测型 DeepResearch Agent。
